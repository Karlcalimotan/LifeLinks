## Contract — `CANCEL_ALERT`

```json
{
  "kind": "CANCEL_ALERT",
  "payload": {
    "incident_id": "llk-1a2b3c4d-00001234",
    "reason": "false_alarm",
    "all_clear": true
  }
}
```

Rules:
- `payload.incident_id` is the **device client incident id** (`llk-...`, generated by
  `newIncidentId()` in the firmware), because that is what the tracker compares with its own
  `g_incidentId`. It is not the server `ImpactEvent.id` (a cuid).
- The queued `DeviceCommand` row carries the server `ImpactEvent.id` in `impactEventId`. The ACK
  route resolves the incident from that column, never from the device payload, so the two id
  spaces cannot be confused.
- Device accepts only while `Countdown` **or** while retrying a dispatched incident.
- Device stops the SMS retry ladder before the next recipient, calls `markAcknowledged()`,
  optionally sends one all-clear SMS to the cached numbers, then ACKs.
- ACK payload: `{ "result": "cancelled" | "too_late" | "unknown_incident" }`. The current
  firmware sends the same value in `detail`; the route accepts either field and prefers `detail`.
- The web sets `FALSE_ALARM` **only** on `result=cancelled`; otherwise it shows
  "device offline / not cancelled" rather than lying. A tracker that never polls is shown as
  expired once the command passes its `expiresAt`, and the operator may send a new request.
- A duplicate request while a live `CANCEL_ALERT` is pending for the same incident is coalesced,
  not queued twice.
- `cancelRequestedAt` on `ImpactEvent` so the UI can show "waiting for device"; it is cleared when
  the tracker answers.
- `CANCELLED` is not overwritten by a late confirmation and an incident with a recorded resolution
  is left as it is. The only local transition left is `CANCELLED → FALSE_ALARM`.
- The platform does not send SMS itself. The device owns the modem and the numbers.

Rationale: this keeps the network out of the emergency path and avoids adding an SMS provider
to the web app.
